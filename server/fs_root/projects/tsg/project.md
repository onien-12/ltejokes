# The Shooting Gallery

Введём 5 понятий:
 - Глобальный сервер - сервер который обрабатывает оплату, email, сохраняет видео, фотографии и чеки после покупки, а также распределяет работу локальных серверов
 - Локальный сервер - сервер, стоящий на одном из заведений клиента, как раз занимающийся управлением устройствами (камерами, терминалами, киосками, и т.д)
 - Камера - всё на самом деле крутится вокруг камер, опишу позже
 - Киоск - устройство для оплаты, которое управляет сессиями оплаты, медиа и терминалами (с фронта, посути делая запросы на локальный сервер)
 - Терминал - терминал оплаты страйпа. Но к терминалам ещё можно отнести экран над киоском, который крутит пока ещё не купленные видео с QR кодом для создания сессии оплаты

## Общая архитектура

Сначала рассмотрим общую архитектуру проекта. На диаграмме ниже представлена иерархия сущностей:
```
                   ┌───────────────┐            
                ┌──┤ Global server ├────┐       
                │  └───────────────┘    │       
                │rgc                    │       
                │                       │       
         ┌──────┴───────┐       ┌───────┴──────┐
     ┌───┤ Local server ├───┐   │ Local server │
     │   └──────┬───────┘   │   └──────────────┘
     │kgc       │advr/lcc   │                   
 ┌───┴───┐  ┌───┴────┐  ┌───┴───┐               
 │ Kiosk │  │ Camera │  │ Kiosk │               
 └───┬───┘  └────────┘  └───────┘               
     │                                          
┌────┴─────┐                                    
│ Terminal │                                    
└──────────┘                                    
```

Рядом с линиями соеденения указаны названия интерфейсов. О них подробнее я напишу позже.
 - rgc - range guard communicator - интерфейс, защищённый с двух сторон двумя связками ключей. Каждый запрос и ответ подписывается сигнатурой (в HTTP Header "Signature"), которая генерируется приватным ключем каждой стороны и каждый запрос и ответ проверяется публичным ключем каждой стороны.
 - kgc - kiosk guard communicator - интерфейс, защищённый со стороны локального сервера, требующий авторизации по токену киоска.
 - advr - AgentDVR Communicator - интерфейс для управления камерами через AgentDVR.
 - lcc - local camera communicator - общий интерфейс для коммуникации между камерой и локальным сервером без использования AgentDVR.
 - Terminal - терминал не имеет как такового интерфейса для прямого управления. Он указывается в базе данных как отдельная сущность, подключается к Stripe и далее глобальный бекенд уже через stripe управляет терминалом.

## Local Server

Локальный сервер, как я и написал ранее - узел, осуществляющий управление всеми устройствами одного заведения. К нему подключаются все камеры, терминалы, киоски и другие устройства. Коммуникация с глобальным сервером осуществляется по интерфейсу rgc.


### Камеры

Так как основная идея локального сервера - управлять устройствами (в основном камерами), то существует очень гибкая система разработки апи для камер - стратегии (я их так называю). Пока их 3: 
 - Lane camera - камера на линии для стрельбы. Распознаёт и сохраняет лица в базу данных, выделяет фотографии и сегменты стрельбы, определяет моменты, когда человек произвел выстрел, записывает мишени, и т.д.
 - Kiosk camera - камера на киоске. Распознаёт лица, понимает какой клиент пришел чтобы отправить эти данные на киоск
 - Другие камеры - их тоже можно разделить на два типа: те, которые сохраняют лица для использования Kiosk Camera'ой и те, которые их не сохраняют, а используются чисто для безопасности.

#### CameraProbeService

Сервис, использующися для нахождения камер в сети. Он запускается самым первым и раздаёт всего две команды: camera.added и camera.removed. На момент запуска системы все предыдущие камеры, которые были подключены считаются отключенными. Так как система сохраняет ip адрес и порт камеры, то можно при нахождении сервисом камер(-ы) сопоставить найденную камеру и уже существующую и принимать решения о дальнейшей инициализации камер.

Работает он так: есть два массива: detectedCameras и connectedCameras. 
 - detectedCameras содержит камеры, пока ещё не покдлюченные к системе. Т.е те, которые были обнаружены (либо хотя бы являются кандидатами на обнаружение) и ожидают процедуры подключение
 - connectedCameras содержит камеры, с которыми уже установлено соединение.

Существует две функции для нахождения камер: subnetProbe и probeCameras. Каждая из них запускается через интервал, который определён в конфигурации (про конфигурацию позже): camera.subnet_probe_interval и camera.probe_interval соответственно. По дефолту эти значения установлены как 60000 и 20000 мсек соответсвенно.
 - probeCameras - основной метод поиска камер. Он основан на том, как работает onvif discovery [https://openconnectivity.org/upnp-specs/UPnP-arch-DeviceArchitecture-v2.0-20200417.pdf]. Существует такой замечательный протокол, UPnP [https://datatracker.ietf.org/doc/html/rfc6970]. Он используется для обнаружения устройств в сети и работает на multicast адресе 239.255.255.250. Все камеры слушают этот адрес и ждут пока на нём появится SOAP сообщение. Так вот всё, что нам надо сделать - это лишь послать пакет на этот адрес и ждать пока нам какая нибудь камера пошлёт ответ.

 - subnetProbe - тестируя, я заметил, что мои китайские камеры не всегда отвечают на запросы UPnP. Но я смог найти решение: открывать соеденение на порт onvif (8899 или 2020) и сразу же его закрывать. После этого камера начинает отвечать на запросы. Именно это функция и делает: она посылает запросы на ВСЕ ip адреса в сети (т.к она не знает на каких из них будут камеры)

Перейдем к описанию работы алгоритма поиска камер:
 - После того, как камеры были определены в сети, система делает попытку подключения к каждой из них (ко всем из detectedCameras). Существует два метода для подключения: node-onvif и onvif. Они немного отличаются по методу подключения, вызывают немного разные функции, туда углубляться не будет. Важно просто знать что оба метода покрывают 99% всех камер. Подключение происходит в функции connect. Опишу процесс подключения подробнее:
  * Сначала система делает запрос на открытие соеденения на порт 8899 или 2020 (эти порты устанавливаются в конфиге camera.onvif.ports). Это улучшает результаты, верьте.
  * Затем производится подключение используя сразу два метода одновременно:
```
        const connection = new Cam({
          ...credentials,
          hostname: ip,
          port,
        });
        const device = new nodeOnvif.OnvifDevice({
          xaddr: `http://${ip}:${port}/onvif/device_service`,
          user: credentials.username,
          pass: credentials.password,
        }); 
```
  * Затем идёт получения Capabilities камеры:
    `await device.getCapabilities().catch(() => null);`
  * Затем мы ждём пока оба соеденения будут установлены и возвращаем их.
 - Все камеры из connectedCameras (т.е те, которые были уже до этого подключены) проходят процедуру проверки соеденения. Посути, это просто один запрос getNTP (<tds:GetNTP/>). Если ответ с камеры не приходит, то камера удаляется из connectedCameras.
 - Подключнные камеры добавляются в массив connectedCameras
 - Камеры, которые были удалены в текущей итерации отправляются вместе с ивентом camera.removed. Камеры, которые были добавлены в текущей итерации отправляются вместе с ивентом camera.added.
```
  const addedCameras = [...newConnectedCameras].filter(
    ([ipPort, cam]) => !this.connectedCameras.get(ipPort),
  );
  const removedCameras = [...this.connectedCameras].filter(
    ([ipPort, cam]) => !newConnectedCameras.get(ipPort),
  );
```

Вся эта процедура повторяется каждые camera.probe_interval миллисекунд (по дефолту, как я и писал ранее, 20000).

Таким образом, система всегда знает какие камеры подключены в любой момент времени.

#### CameraEventService

Достаточно простой сервис, задача которого заключается в обработке ивентов camera.added и camera.removed.

При получении ивента camera.added вызывается функция cameraAdded. В ней выполняются следующие действия:
 - Ищется уже существующая камера. Если она была найдена, то пробрасывается дальше в OnvifService.setupCamera. Если нет, то пробрасывается туда вместо камеры null.
 - Если камера существует, то она помечается как connected.
 - Если её не существует, то она создаётся и настраивается с помощью OnvifService.setupAgentdvr и OnvifService.setupCameraTexts.

При получении camera.removed производятся следующие действия:
 - Камера удаляется из OnvifService.devices.
 - Камера помечается как connected: false и закрывается поток.
 - Устанавливается дата отключения камеры (это пригодится потом в CameraScheduleService)

#### OnvifService

Сервис, являющийся основной точкой вызова всех настроечных функций. Именно здесь настраивается AgentDVR, распознование лиц, потоки, а также производятся дополнительные запросы на камеру.

Главной функцией является setupCamera. Рассмотрим её подробнее:
 - Эта функция получает объект камеры в базе данных (опционально), и два соеденения с CameraProbeService.
 - Определяется список onvif профилей камеры. Это необходимо для определения URL RTSP потока:
```
  let profiles = await device
      .mediaGetProfiles()
      .then(() => device.mediaGetStreamUri())
      .then(() => device.getProfileList());
  let stream = profiles[0].stream.rtsp;
```
 - Затем запускаются обработчики стратегий:
  * Если установлен флаг is_at_kiosk, то вызывается функция CameraStreamService.startKioskStream
  * Если установлен lane_name, то вызывается функция CameraStreamService.startLaneStream
  * Если ничего из этого не установлено, то камера помечается как streaming: false и эта процедура проверки больше не запускается.
 - После этого камера добавляется в OnvifService.devices, вызывается setupAgentdvr и setupCameraTexts.

setupAgentdvr использует AgentDVRService для настройки камеры, этот этап будет рассмотрен далее в разделе про AgentDVRService.

setupCameraTexts удаляет текста, которые камера добавляет к потоку. Эти текста называются OSD (On-Screen Display). ONVIF имеет функции для их удаления, именно это и делает эта функция:
 - Запрашивает список OSD у камеры
 - Проходится по каждому и удаляет этот OSD.
```
const osds = (await device.getOSDs()) ?? []

await Promise.all(osds.map((osd) => 
  device.deleteOSD(osd.token)
))
```

#### AgentDVRService

Все камеры, какими они ни были бы, являются камерами для безопасности. Существует два инструмента, которые используются для осуществления функций контроля: AgentDVR и go2rtc
```
            ┌──────────┐ ┌────────┐   ┌────────┐     
            │ AgentDVR ├─┤ Camera x───┤ go2rtc │     
            └────┬─────┘ └────────┘   └────x───┘     
                 │                         │         
          ┌──────┴──────────┐ ┌────────────┴────────┐
          │ AgentDVRService │ │ CameraWebrtcService │
          └─────┬───────────┘ └────────────x────────┘

                │   ┌──────────────────┐   │         
                └───┤ WebrtcController x───┘         
                    └──────────────────┘             
                     /camera/:id/webrtc               
```
go2rtc УЖЕ не используется, поэтому даже рассматривать его не буду.

AgentDVR - инструмент для управления камерами. Позволяет настроить все функции безопасности: управление поворотом, автоматическая запись при обнаружении движения, timelapse, и т.д.
У AgentDVR есть API, интерфейс для него назван advr. Этот интерфейс реализован в AgentDVRService. На следующей диаграмме показана иерархия классов и методы для advr:
```
┌─────────────────┐     ┌──────────────────────┐
│ AgentDVRService │     │ AgentDVRCommunicator │
└─────────────────┘     └──────────────────────┘
┌───────────┐           ┌──────────────────┐    
│ addCamera │           │    addCamera     │    
└───────────┘           │/command/addOnvif │    
                        └──────────────────┘    
                        ┌──────────────────┐    
                        │    cameraOn      │    
                        │/command/switchOn │    
                        └──────────────────┘    
 ┌─────────────────┐    ┌───────────────────┐   
 │ getCameraObject │    │     getObjects    │   
 └─────────────────┘    │/command/getObjects│   
                        └───────────────────┘   
 ┌───────────────┐      ┌───────────────────┐   
 │ getMjpgStream │      │   getMjpgStream   │   
 └───────────────┘      │/command/video.mjpg│   
                        └───────────────────┘   
```
Определим также один тип: 
```
interface AdvrObject {
 oid: number; // id объекта в AgentDVR
 ot: number; // тип объекта (2 - камера, 1 - звук)
}
```

 - addCamera - осуществляет добавление камеры. Принимает такие параметры, как: uri (адрес эндпоинта ONVIF), name (название камеры), substream/mainstream (номера профилей в onvif для получения потока для записи и live streaming'а соответсвенно), username/password (данные для авторизации для получения видео или управления камерой), и т.д. Возвращает AdvrObject
 - cameraOn - осуществляет инициализацию камеры в AgentDVR. Принимает AdvrObject и ничего не возвращает.
 - getObjects - возвращает все объекты в AgentDVR (AdvrObject[])
 - getMjpgStream - возвращает видео поток с камеры в формате mjpg. Принимает список id объектов (oid) и размер каждого видео.
 - AgentDVRService.getCameraObject - получает один объект камеры в AgentDVR по id камеры в нашей системе. Работает это с помощью того, что при создании камеры наша система указывает name как `Camera|{id}`. Функция получает список всех AdvrObject, затем фильтрует этот список по полю name и возвращает подходящие объекты (ожидается всего два объекта: один для видео потока, другой для аудио).

После выполнения этой процедуры камера будет добавлена в AgentDVR, настроена и будет готова для использования.

#### CameraStreamService

Этот сервис является основным распределяющим сервисом для всех функций, свзанных с распозвованием лиц, записью сегментов стрельбы, определения клиентов, и т.д. По своей сути он занимается только проверкой разных условий и запускает CameraLaneService или CameraKioskService. Помимо этого, в его задачи входит хранение информации о камерах, для которых в текущий момент запущено какое либо распознование.

Существует два основных метода: startStream и destroyStream. По названию можно догадаться, что первый метод запускает обработку камеры, а второй наоборот - останавливает.

startStream уничтожает предыдущий поток и запускает новый с помощью CameraLaneService.createReceiver или CameraKioskService.createReceiver, при этом камера помечается как streaming
```
await this.destroyStream(camera);
this.streamingCameras.set(camera.id, {
  lane: true,
});
await this.crudService.updateCamera(camera, { streaming: true });
if (camera.lane_name)
  this.laneService.createReceiver(camera, camera.stream_url);
else
  this.kioskService.createReceiver(camera, camera.stream_url);
```

destroyStream же просто уничтожает поток и помечает камеру как streaming: false

#### CameraKioskService и CameraLaneService

Два сервиса, которые отвечают за сбор конфигурационных значений и передачу исполнения FaceDetectService'у. FaceDetectService в свою очередь запускает worker и сейчас давайте разберемся что такое worker и как он работает в системе.

В общем в nodejs есть модуль, worker_threads [https://nodejs.org/api/worker_threads.html], который позволяет создать отдельный поток либо процесс и независимо от основного потока выполнять код. Таким образом, worker позволяет полностью отделить выполнение кода и ускорить его в несколько раз, так как event loop не будет ждать, пока выполняться задачи других функций.

Event loop можно условно представить как очередь операций. Если эту очередь нагрузить обработчиками, например, 20 камер, то всё будет работать очень медленно и плохо. Поэтому можно создать ещё 20 очередей в отдельных потоках и тогда они будут работать независимо друг от друга, а соответсвенно и намного быстрее. Однако с официальной библиотекой есть проблема: при попытке импорта opencv4nodejs (библиотека для обработки видео, поговорим о ней позже) возникает ошибка. Она связана именно с методом, как worker_threads организует запуск отдельных потоков и изменить это никак нельзя. Тут я придумал такое костыльное, но решение: запускать отдельный ПРОЦЕСС. Процесс отличается от потока тем, что он - скорее отдельный конструкт операционной системы, нежели поток. 

Так вот. Обмен данными между процессами у меня обеспечивает stdout и stdin (это два основных системных файла, которые существуют для каждого процесса) (файла, потому что в unix всё - файл). Идея проста: записывать какой нибудь json объект в stdin чтобы послать данные в worker и записывать объект в stdout чтобы послать данные из worker.
```
  {                                              
    camera,                                      
    streamURI,     ─────┐                        
    config: { ... }     │                        
  }                     │                        
┌──────────────┐        ▼ stdin┌────────────────┐
│              ├──────────────►│                │
│              │               │                │
│ Main process │               │ Worker process │
│              │               │                │
│              │◄──────────────┤                │
└─────────┬────┘         stdout└────────────────┘
          │                 ▲                    
          ▼                 │                    
 emit(event, data)   {                           
                       numFaces: number,         
                       gotFaces: number,         
                       camera: CameraContext     
                     }                           
```

На диаграмме показано, что главный процесс запускает worker, в stdin записывает данные, а из stdout считывает и перенаправляет их в eventEmitter2. Ожидается, что в один момент времени будет записано не более двух объектов.

#### Detection workers

Мы подошли к первому чекпоинту: скрипты, которые занимаются поддержкой состояния для каждой камеры. Например Lane Detection Worker в каждый момент времени знает, есть ли кто-нибудь на линии для стрельбы, или нет.

Для начала надо понять как вообще можно добиться потока видео (даже с самым большим разрешением) практически в реальном времени (< 100ms delay). В этом помогает ffmpeg, opencv и оптимизация практически всего. 

Каждый worker для получения видео вызывает функцию prepareStream. Именно она занимается организацией всего, что необходимо для ПОЛУЧЕНИЯ потока в реальном видео. 
 - Первым делом запрашивается информация о потоке: getStreamInfo. 
  * getStreamInfo вызывает ffprobe. Ffprobe является отдельной программой для считывания метаданных любых потоков
  * Из этих данных нам необходимо получить только размер видео (ширину и длину), fps мы знаем из OnvifService
 - Затем строится массив crop | 0, 0, width, height |. Он будет определять какой участок видео будет обрезан. Это необходимо для условий, при которых часть другой линии попадает на камеру
 - После этого строится detectionConfig, в котором собираются все известные нам данные: useLiveModel, scaleFactor, minFaceSize (об этом позже)
 - Следующим шагом является запуск ffmpeg. Параметры были подобраны самым лучшим образом: 
  * Параметры потока:
   1. -fflags nobuffer - отключает rtsp буфферизацию. Ffmpeg не будет стараться записывать кадры в буфер для обработки, а будет прям сразу их выдавать. Уменьшает задержку, но ухудшает стабильность (но это того стоит)
   2. -flags low_delay - убирает дополнительные процедуры для обработки кадра, что тоже улучшает скорость
   3. -strict experimental - убирает проверки потока, снижает общие требования к кадрам и улучшает за счет этого скорость
   4. -rtsp_transport tcp - не влияет на скорость, зато очень сильно улучшает стабильность засчет использования TCP вместо UDP (не буду здесь писать, почитайте в проекте про ОС, там страниц 10 написано только про TCP)
   5. -probesize 32 - устанавливает количество байт, которое ffmpeg будет использовать для анализа потока. Меньше - быстрее. На стабильность особо не влияет
  * Выходные параметры
   1. -pix_fmt gray - формат вывода. Так как сам worker считывает чистые байты из stdout ffmpeg'а для преобразования их в матрицу картинки, то есть смысл передавать минимальное кол-во байт между процессами для снижения нагрузки на процессор. Также это переносит функцию по переводу матрицы картинки из 3-х канальной в 1-канальную с nodejs на ffmpeg, что ускоряет в целом всю процедуру.
   2. -vcodec rawvideo - устанавливает кодек видео для выдачи чистых значений яркости каждого цвета (но так как pix_fmt=gray, будет просто один канал - яркость одного пикселя, т.е черно-белая картинка).
   3. -f rawvideo - то же, что и 2
   4. -vf - фильтр видео. Их несколько:
    1) crop='min({w},iw)':'min({h},ih)':{x}:{y}' - применяет массив crop к видео
    2) scale='iw/{camera.config.scaleFactor}:-1' - меняет размер видео, при этом сохраняя aspect ratio
    3) rotate='{rot} * PI/180' - применяет поворот к видео, что может использоваться для компенсации поворота камеры
   5. -an - удаляет звук из видео. Для распознования лиц он всё равно не нужен
   6. -sws_flags fast_bilinear - устанавливет метод применения scale к видео. fast_bilinear немного ускоряет применения vf
   7. -threads 1 - накладывает ограничение на потребление процессора
 - Определение количество байт, требующееся для чтения с ffmpeg чтобы получить один frame: vw * vh * c, где c = 1 (кол-во каналов), vw и vh -  ширина и длина кадра соответвенно.

Теперь как только мы понимаем как с помощью ffmpeg мы получаем поток в реальном времени, давайте рассмотрим два метода Face Detection (т.е нахождения координат лица в кадре). Этим занимается функция face-utils.tools.ts/detectFaces.
 - Cascade Classification - одновременно простой, эффективный и очень шустрый метод обнаружения лиц. Для него используется функция opencv.CascadeClassifier.detectMultiScale. На вход она принимает:
  * Mat - матрицу изображения
  * config.scaleFactor - фактор изменения разрешения, который будет применяться к изображению перед классификацией. Чем больше тем быстрее будет выполняться функция, но тем менее точными будут результаты. По моим тестам - 1.4-1.6 должно быть в самый раз - минимальное время выполнения и нагрузка на процессор с наилучшими результатами.
  * minNeighbours - количество соседних 9x9 ячеек для проверки результата. Чем больше - тем точнее результат, но тем будет медленнее. Лучше всего работает 3.
  * Flags - дополнительные параметры, пока нас не интересуют
  * minSize - параметр config.minFaceSize - указывает минимальный размер лица в px которое алгоритм будет пытаться искать. Чем больше площадь - тем быстрее, но на дальних расстояниях может упускать лица. Оптимальнее всего работает [100, 100]
 - Object matching - более сложный, менее быстрый, но очень точный метод обнаружения лиц. Работает на основе анализа кадра нейросетью, я использовал модель MediaPipe BlazeFace. Также опционально можно включить:
  * Модель MediaPipe Iris - для отслеживания положения глаз, а следовательно и отслеживания направление лица, а значит и делая более точные предсказания при распозновании.
  * MediaPipe FaceMesh - для отслеживания 3д модели лица и получения очень точных данных по лицевым деталям. Даёт возможность делать более точные данные при распозновании.
  * Liveness и Real-Or-Fake (LivenessNet) - используется для определения, использует ли человек инструменты для обмана распознования лиц (например телефон с фоткой лица).
 Каждая опция влияет на производительность, поэтому изначально они все выключены и включить их можно ТОЛЬКО в коде. Рассмотрим работу BlazeFace:
  * В модель загружается один 4-х мерный тензор (значит rgba, добавляется канал для прозрачности):
   1. Над изображением производится операция rescale: tf.image.resizeBilinear
   2. Матрица нормализуется и загружается в модель: model.execute(tf.sub(tf.div(image, 127.5), 1))
  * Модель выдаёт одну матрицу, содержащюю все нужные данные. Постараюсь описать проще:
   1. Генерируем anhors. Модель не выдаёт номера пикселей, она делит картинку на отдельные регионы и выдает номер одного из них. Номер региона можно перевести в координаты. Пиксель региона определяется его верхней левой точкой, именно определением какие регионы есть и какие пиксели они занимают и занимается алгоритм нахождения anchors.
   2. Находим anchor центра найденного лица. Модель возвращает одну область в виде матрицы | axcl aycl awl ahl |, где axcl, aycl - координаты центра области под номером l; awl, ahl - ширина и высота области l
   3. Переводим anchor координаты в координаты пикселя: 
    xcl = axcl / x_scale * aw + ax
    ycl = aycl / y_scale * ah + ay,
   где aw, ah - ширина и длина anchor; ax, ay - координаты центра anchor. Если мы представим в голове себе сетку, то всё получается логично: двигаемся ax пикселей (т.е получая координату центра anchor) и перемещаемся ещё axcl * aw, как добавочное движение отношения размера пикселя к размеру сетки.
   4. Находим координаты региона:
    xl = xcl - wl / 2
    yl = ycl - hl / 2
   тут тоже логично: найдя центр региона, нам надо переместиться назад wl / 2 и yl / 2 пикселей чтобы попасть в начальную точку.
   5. Набор xl, yl, wl, hl и будет являться нашим регионом лица.

Понимая, как можно получить набор областей с лицами, давайте теперь уже перейдем непосредственно к алгоритму worker'ов


##### Lane Worker:
  1. Считывается кадр: `video.read(dims.bytes)`
  2. В конфиге есть значение camera.skipNFrames, которое задает кол-во пропускаемых кадров (если skipNFrames = 1, нагрузка на процессор будет на 50% меньше, но точность тоже станет меньше). Номер кадра проверяется условием: `iteration % (skipNFrames ?? 0) + 1 === 0`. Если true, то идем далее.
  3. Сбрасываем framesWithoutFaces, если значение больше чем 2^12
  4. Кадр дополнительно обрезается и принимает размер camera.targetWidth ?? 1200 пикселей
  5. Производится поиск лиц с помощью detectFaces.
  6. Если лица найдены И кол-во кадров подряд с лицами больше 10, framesWithoutFaces = 0
  7. Если не найдены, то framesWithoutFaces = 0 и faceSequence = [] (т.е сбрасываем массив с областями лиц, идущих подряд)
  8. Проходимся по каждому лицу и:
   1) Если faceSequence.length === 10, добавляем в массив faces все накопленные лица в faceSequence и текущее лицо
   2) Если faceSequence.length > 10, добавляем только текущее лицо в массив faces
   3) Добавляем лицо в faceSequence
  9. Если faceSequence.length > startFaces / (skipNFrames ?? 0) + 1, (т.е набралось достаточное кол-во лиц подряд для того, чтобы считать, что клиент пришел на линию), то:
   1) Блокируем все распозновния на одну итерацию (пока не будет установлен флаг personInLane). Это надо, потому что распознование асинхронно и пока производятся операции в этой процедуре, она может в другом потоке быть выполнена повторно, чего надо избежать.
   2) Текущий кадр распознаётся с помощью Object matcher (т.е ИИ). Это надо для случаев, когда classifier даёт очень ненадёжные данные. Object Matcher гораздо надёжнее, но медленнее, поэтому запускается он один раз и только здесь (если useLiveModel = false, иначе detectFaces будет всегда использовать object matcher).
   3) Если лицо найдено, то отправляем face_detect.start на основной поток и ставим personInLane = true
   4) Иначе, faceSequence = [], personInLane = false
 10. Если framesWithoutFaces >= maxNoFaces / (skipNFrames ?? 0) + 1 && personInLane (т.е на кол-во кадров без лиц уже достаточно большое, чтобы считать, что человек покинул линию и человек был на линии), то
   1) FFMPEG завершает работу: `ffmpeg.kill('SIGTERM')`
   2) Отправляется face_detect.finished на основной поток
   3) Все лица сохраняются в отдельную директорию, которая была создана на этапе 9 (когда клиент пришел)
   4) Worker завершает работу: `process.nextTick(() => process.exit())`

При получении face_detect.start, выполняется функция StartLaneRecordingService.onFaceDetectionStart:
 1. Генерируется faceId (рандомное число до 10^7)
 2. В базе данных создаётся клиент с face_id = faceId, is_on_lane = true, cameraId = event.camera.id
 3. Создаются все нужные директории и отправляются на worker (сообщение client.directories)
 4. Создаётся файл полной записи сессии
 5. Запускается ffmpeg с помощью RecordingService.createVideoProcessor:
  - -f matroska - сохраняет видео в формат .mkv
  - -rtsp_transport tcp, -max_muxing_queue_size 8192 - я объяснял до этого
  - -c:v copy - сохранение кодека. Ускоряет выполнение в кучу раз (реально во много раз)
  - -af silencedetect=n=${silencedb}dB:d={peakDelta} - настраивает ffmpeg давать данные о сегментах с тишиной. Данные посылаются в stderr ffmpeg'а в формате `[silencedetect @ 000002ef899fcc80] silence_end: 8.39663 | silence_duration: 2.187`. 
 6. Настраивается парсинг сообщений о сегментах с тишиной (это которые -af). Каждый сегмент сохраняется в сессию в silenceSegments
 7. Устанавливается функция, которая будет вызвана в случае окончания работы ffmpeg. Она отправит сообщение face_detect.ffmpeg.finished в EndLaneRecordingService. Это надо будет позже.

При получении face_detect.finished вызывается EndLaneRecordingService.onFaceDetectionFinished:
 1. Создаётся новый поток для приёма видео и обработки лиц (помним, он закрылся сам (10 пункт, 4 подпункт)).
 2. FFMPEG завершает работу: `utilsService.killFfmpeg(session.videoProcessor)`
 3. Если 20 лиц не было получено, устанавливается session.isNoFaces = true, клиент и все записи удаляются.
 4. Иначе, ждем пока закроется ffmpeg и пришлет face_detect.ffmpeg.finished

При получении face_detect.ffmpeg.finished вызывается EndLaneRecordingService.sessionFinished:
 1. В базе данных клиент помечается как is_on_lane = false
 2. Начинается процесс обучения модели для распознования лиц (про это вообще позже позже)
 3. Сегменты тишины инвертируются с помощью функции utils/ffmpeg.tools.ts/invertSegments (т.е превращаются в сегменты НЕ тишины, т.е выстрелы)
 4. Сегменты удлиняются до 2 * peakDelta секунд и сливаются, если удлиненные сегменты накладычваются друг на друга. Это делает функция utils/ffmpeg.tools.ts/extendAndMergeSegments.
 5. На основе сегментов НЕ тишины генерируются фотографии (т.е это будут фотки клиента ПРЯМО в момент выстрела). Делается это с помощью ffmpeg:
  - -vsync 0 - отключает vsync, чтобы при извлечении кадра не было разрыва
  - -vf select='lt(prev_pts*TB\,{t})*gte(pts*TB\,{t})' - в фильтре select указываются значения времени кадра (это t). Не получится просто сделать сравнение как eq({t}\,start_t), т.к в видеопотоке может просто не быть кадра с нужным временем, поэтому здесь мы выбирает самый близжайший кадр к времени t.
  - frame_%d.jpg - сгененрированные кадры будут иметь индекс (т.е имя файла будет frame_0.jpg, frame_1.jpg, и т.д).
 6. Сгенерированные кадры переименовываются чтобы включать имя кадра (frame_1.jpg -> frame_7.621.jpg). Потом имя файла будет использоваться чтобы быстро получать кадры и не генерировать из заново каждый раз когда они нужны
 7. Для каждого сегмента в базе данных создаётся запись и из полного видео извлекается нужный сегмент.

После всей этой процедуры у нас есть:
 1. id клиента, id его сохранённых лиц.
 2. Модель для распознования лиц.
 3. Кадры в моменты стрельбы.
 4. Записанные сегменты стрельбы.
 5. Полная запись его сессии.

Далее киоск может получить эти данные используя эндпоинт GET /client/all - он возвращает всех клиентов, их видео и фотографии.

##### KioskWorker

KioskWorker работает проще: он ждет пока наберется 20 кадров с лицами, потом ждет 15 секунд и снова ждет пока наберется 20 кадров с лицами. Здесь стоит понимать уже процедуру обучения модели и самого распознования:

Обучение модели - это посути получение Face Landmarks и их сохранение в файл. Именно это и делает recognition/train.worker.ts. Он выбирает несколько лиц по формуле:
i % r(0.05L * sigf(-0.001L)) == 0, L > 60                                         
true, otherwise,

где i - индекс лица, r - операция округления, sigf - функция сигмоида на числа с плавающей точкой, L - кол-во лиц.
Затем с помощью FaceMesh у всех этих лиц получаются Face Landmarks и они сохраняются в matcher.json прямо в директории с лицами.

При получении списка лиц с KioskWorker'а производится этап Recognition. По факту мы для каждого поступившего лица находим landmarks и сравниваем их стандартной девиацией со всеми сохранёнными landmark'ами, пока не получим совпадение. Организовано это так:
 1. При старте системы создаётся camera.recognition.workers_num worker'ов для распознования лиц. Каждый worker принимает два лица - те, которые надо сравнить.
 2. При поступлении N лиц, система выберает Ns лиц, проходится по каждому клиенту, собирает сохранённые face landmarks и направляет все эти лица по каждому из workers_num worker'ов
 3. Каждому worker'у направляется два лица и processId (уникальный id процесса, который уникален для сравнения с одним клиентом. Т.е мы сравниваем Ns лиц, производя Ns вызовов recognition.worker.ts, для каждого клиента. И для каждого клиента имеется свой уникальный processId).
 4. После накопления Ns результатов распознования (которые приходят по ивенту face_recognizer.recognize.finished и вызывают FaceRecognitionService.onRecognitionResult), вычисляется среднее арифметическое результатов схожести лиц (при этом если схожести нет даже в одном результате, средняя схожесть делится на 2) и сравнивается с camera.recognition.similarity_level.
 5. Если средняя схожесть больше, чем similarity_level, то отправляется face_recognizer.recognize.finished и id клиента, лицо которого совпадает с лицом на киоске (мы знаем id клиента по processId, который всё это время был одинаковый для каждого клиента).
 6. CameraSocketGateway.onFaceRecognized принимает сообщение и направляет по websocket'у на фронтенд, где открывается нужный клиент.

### rgc

Мы рассмотрели (почти) всё, что связано с камерами. Там я не стал писать о RecordingModule, WebrtcModule и ещё о некоторых модулях, но это не столь важно. И перед тем, как мы перейдем к части, которая связана с обработкой покупок, статистики, админки, конфигурации, автонастройки, где всё будет работать совместно с глобальным сервером, надо сначала понять как вообще локальный и глобальный сервер между собой коммуницируют.

Протокол rgc универсален: он добавляет всего два значения, которые могут быть переданы используя любой протокол, будь это HTTP или websocket'ы. Я изначально начал использовать HTTP, реализован только он, поэтому будем говорить о нем. Проект построен так, что rgc реализуется только в одном месте - и это репозиторий rgc-communicator, который содержит небольшой модуль буквально на 200 строк кода, который обрабатывает аутентификационные функции протокола.

rgc по сути выполняет только функции безопасности и авторизации пользователей. Локальному серверу нет никакого дела до того, какие пользователи есть в системе в целом и нужен механизм, как можно внести ограничения определённым пользователям на доступ к локальному серверу. И сделано это так:

Локальный сервер принимает ТОЛЬКО запросы с глобального сервера (и киоска, но это редко). Проверкой запросов занимается GlobalServerGuard, о нем позже. В запросе пробрасывается вся информация о пользователе, а именно:
 - Роль пользователя (является ли он владельцем или имеет другую роль)
 - Другие данные, такие как email, id, имя, и т.д, это не особо важно.
Локальный сервер проверяет два поля: isSGO и isOwner и на их основе он принимает решение об обработке запроса. Этим занимается UserGuard и он ещё может проверять на дополнительные два декоратора: OnlyGlobalAdmin и OnlyOwner, которые разрешают делать запросы только глобальному админу и владельцу стрельбища соответсвенно.

Но как локальный сервер знает, был ли запрос сделан с глобального сервера или нет. Это работает с помощью криптографии. rgc реализует свою собсветнную систему управления ключами. При создании стрельбища, глобальный сервер создаёт две пары ключей: g_pkey_checker, g_skey_signer и l_pkey_checker и g_skey_signer:
 - g_pkey_checker и l_pkey_cheker - два ключа, которые нужны для *проверки* запроса.
 - g_skey_checker и l_skey_checker - два ключа, которые нужны для подписи запроса (т.е создания сигнатуры).

Так вот, локальный сервер получает связку l_pkey_checker и l_skey_signer, а глобальный, соответсвенно, g_pkey_checker и g_skey_signer. С помощью signer ключа сторона может подписать свой запрос, а с помощью checker ключа другая сторона может проверить, был ли запрос подписан нужным ключем. Signer держится в строгом секрете и никто его не знает, даже сам глобальный сервер не знает l_skey_signer. Сигнатура записывается в HTTP Header "Signature". 

Тут вы можете спросить: а что будет если один и signer ключей утечет, допустим l_skey_signer? Да, это проблема и это будет значить, что любой человек сможет делать запросы на глобальный сервер как будто это делает сам range (где соответсвенно утёк ключ). Я мог бы ответить, что ну это всего одно стрельбище, не проблема, поменяем ключи, но нет. Есть ещё один этап защиты. Он заключается в алгоритме генерации исходного текста для хеширования. Даже если утечёт ключ, алгоритм всё равно никто не знает и раскрывать я его не буду.

Давайте теперь уже перейдём от теории к практике и рассмотрим работу протокола в действии:
```
      {                                       
       _internal: {                           
        isSGO: false,                         
        isOwner: true                         
       }                                      
      }                                       
      alg(...), g_skey_signer                 
┌───────┐        │      ┌────────┐            
│ Range │        │      │ Global │            
└───┬───┘        │      └────┬───┘            
    │            ▼           │ /api/camera/all
    │      /camera/all       │◄──────────     
    │◄───────────────────────┤                
    │   Signature: hash(k)   │                
  ┌───┐                      │                
  │ 1 │                      │                
  └───┘                      │                
    │  OK, Camera[]          │                
    ├───────────────────────►│                
    │ Signature: hash(lk)    │                
    │          ▲           ┌───┐              
    │          │           │ 2 │              
    │          │           └───┘              
    │alg(...), l_skey_signer │ OK, Camera[]   
    │                        ├──────────►     
    │                        │                
    │                        │                
    │                        │                
    │                        │                
                             │                
```

Это значит, что:
 - Пользователь делает запрос на глобальный бекенд на POST /range/{id}/api/camera/all
 - Глобальный бекенд обрабатывает авторизацию пользователя и указывает эти данные в запросе на локальный сервер на POST /camera/all
 - Запрос дальше подписывается с помощью g_skey_signer, хеш записывается в HTTP Header "Signature". Это делает SignerInterceptor
 - Локальный сервер выполняет процедуру [1] (GlobalRequestGuard). В ней составляется тот же plaintext по тому же алгоритму, как это делает глобальный сервер, а затем сигнатура проверяется с помощью l_pkey_checker. Если сигнатура совпадает, то пропускаем запрос и идём дальше.
 - Локальный сервер дальше проверяет _internal. Смотрит на поле isOwner, понимает, что запрос идёт от владельца стрельбища и идёт далее. Это делает UserGuard и OnlyOwner.
 - После обработки запроса, ответ также подписывается уже со стороны локального сервера своим секретным ключем l_skey_signer. Хеш записывается в HTTP Header "Signature". Этим занимается SignerInterceptor
 - Ответ также проверяется глобальным сервером с помощью своего ключа g_pkey_checker в процессе [2].
 - Если всё нормально, то пользователю посылается ответ, который содержит ответ локального сервера.

Итого, rgc позволяет:
 - Абстрагировать проверку на авторизацию и работу с правами пользователя дальше от локального сервера и передать эти обязаности глобальному серверу (что конечно же улучшает безопасность)
 - Полностью обезопасить коммуникацию использованием сигнатур (то есть этих вот двух пар ключей и секретного алгоритма (который на диаграмме был обозначен как alg))
 - Скрыть настоящий адрес локальных серверов, что тоже сильно улучшает безопасность.
 - Ограничить область взаимодействия с локлальным серверов, что тоже улучшает безопасность.

### ConfigModule

Модуль хранения конфигурации. Используется вообще везде в системе. Вы могли это заметить, когда я описывал камеры. Там я приводил значения как раз и конфигурации. Сейчас мы рассмотрим метод хранения данных, кеширования и взаимодействия с ними (с данными то есть).

Начнем с того, что я не использовал никакой mongodb или любой другой nosql аналог. Мне было достаточно лень писать ещё схемы для mongoose и т.д. Поэтому значения конфигурации просто хранятся в отдельной таблице в postgresql в одном поле типа json.

Можно заявить, что "это неэффективно, sql базы не предназначены для этого" или "ты будешь делать запрос каждый раз ахахах", но у меня есть ответы на такие заявления:
 1. пофиг
 2. Поэтому ConfigModule реализует кеширование. По факту - это просто загрузка конфигурации в оперативную память и использование её оттуда. Сделано это так:
  - Первый раз при вызове ConfigService.get или ConfigService.set конфигурация реально подтягивается из базы данных и сохраняется в оперативную память
  - Второй раз при вызове ConfigService.get значение берётся из оперативной памяти
  - Каждый раз при вызове ConfigService.set значение меняется как в оперативной памяти, так и в базе данных.
  - Таким образом, мы сохраняем актуальность конфигурации в двух местах, при этом оптимизируя самую важную функцию, которая вызывается наиболее часто: ConfigService.get

Вы заметили, что я упомянул json выше. Да, каждое поле - это json, а значит можно хранить списки, объекты, строки, числа и всё, на что способен json. Возьмем в пример camera.onvif.ports: его дефолтное значение: [8899, 2020].

Стоит также упомянуть про настройку конфигурации. Её производит не пользователь, она автоматическая и вызывается из SetupService.setupConfig. В этой функции устанавливаются все дефолтные значения всей конфигурации. А сама эта функция вызывается из SetupService.setup, а она вызывается из SetupController.setupRange, а это вызывается при запросе с глобального сервера на создание range. Но об этом позже.

3. camera.detection.lane.min_faces: Specifies the minimum amount of faces required on the lane camera for the system to save recordings and train the recognizer. Recommended value: 20-40.

### PaymentModule

PaymentModule - модуль, который обрабатывает всё, что связано с покупками (логично, не так ли). Работает он очень тесно с глобальным сервером, т.к именно глобальный сервер хранит ключ от stripe и взаимодействует с ним. Описывая этот раздел, я намеренно опущу детали работы PaymentModule на глобальном сервере, их распишу в отдельном разделе.

Сначала определимся что нужно клиенту:
 1. Покупка фото и видео их стрельбы с киоска вручную через создание сессии, ввод email'а прямо на киоске, и т.д.
 2. Обработка дополнительных платежей
 3. Покупка фото и видео через сканирование qr кода на тв без отдельного создания сессии. Тоесть на тв будут крутиться фотки и видео, которые были записаны И не были куплены и рядом qr код, который можно сканировать, чтобы прям сразу купить одно видео или фото.

При этом у пользователя должна быть возможность оплаты как по qr коду, так и через терминал (если есть и если на киоске).

Учтите, что требования могут добавляться (как это было с 3 пунктом), а значит модуль обработки оплат должен быть максимально гибким, чтобы покрывать все потребности клиента.

Ну и я реализовал это так:

На локальном сервере мы храним сессии оплаты в отдельной таблице: PaymentSession. Она имеет следующую структуру:
```
{
  id Int @id @default(autoincrement())
  video_ids Int[]
  /// [PhotoDefinitions]
  photos Json @default("[]")
  additional_products String[]
  uid String @default(uuid())
  active Boolean
  kiosk Kiosk
  clients Client[]
  createdAt DateTime @default(now())
}
```

при этом PhotoDefinitions определён в types.d.ts так:
```
export class PhotoDefinition {
  timestamp: number;
  client_id: number;
}
type PhotoDefinitions = Array<PhotoDefinition>
```

И отсюда выходит CreateSessionDto: 
```
export class CreateSessionDto {
  email: string;
  client_ids: number[];
  video_ids: number[] = [];
  photos: PhotoDefinition[] = [];
  additional_products: string[] = [];
}
```

Таким образом для создания сессии надо заполнить:
 1. email - email клиента соответственно
 2. client_ids - id пользователей в системе, для которых осуществляется покупка
 3. video_ids - id всех покупаемых видео
 4. photos - массив всех покупаемых фоток (timestamp берется их полного видео клиента)
 5. additional_products - дополнительные продукты, которые человек приобрел. Добавляются к стоимости и обрабатываются дополнительно. Пока это сделано как id товара в stripe.

В модели клиента тоже есть additional_products, это тоже дополнительные продукты, которые администратор назначил пользователю вручную или система автоматически сделала это. Например, счет в кафешке или какая нибудь другая услуга.

#### Создание сессии

При получении запроса на POST /payment/create_session, локальный бекенд создаёт сессию и возвращает url для оплаты. Рассмотрим алгоритм создания сессии:
 1. Получаются все нужные entity из базы данных: видео, клиенты, киоск, и т.д
 2. Рассчитывается общая стоимость покупки:
  B_v * L_v + K_vd * sum(i){D[i]} +
  B_p * L_p +
  sum(i){A[i]},
 где B_v, B_p - базовая стоимость одного видео или фото, L_v, L_p - количество видео или фото, K_vd - коэфициент длины видео (другими словами стоимость одной секунды) (определяется параметром payment.video.duration_coef), D[i] - длительность i'того видео, A[i] - стоимость i'того дополнительного продукта. Надо учесть, что A[i] добавляется на ГЛОБАЛЬНОМ бекенде, а не на локальном.
 3. На глобальный бекенд отправляется запрос со стоимостью, email, id сессии и id терминала (если есть. Его локальный бекенд получает из id киоска, а к киоску может быть привязан только один терминал)
 4. Глобальный бекенд возвращает данные покупки и локальный бекенд формирует запрос
```
          ┌───────┐          ┌────────┐
          │ Range │          │ Global │
          └───┬───┘          └────┬───┘
create_session│                   │    
─────────────►│                   │    
              │/create_payment    │    
              ├──────────────────►│    
              │{                  │    
              │ price, session_uid│    
              │ email, reader_id  │    
              │}                  │    
              │  OK               │    
              │◄──────────────────┤    
 OK, { link } │CreateSessionResponse   
◄─────────────┤ {                 │    
              │  id, uid, url,    │    
                 range_session_uid     
                }                      
```

Запомните существование двух uid: на глобальном бекенде и на локальном бекенде они не зря разные, и не зря глобальный бекенд хранит uid, который на локальном бекенде (это range\_session\_uid).

#### Payment webhook

Вот мы создали сессию, получили url, клиент там допустим оплатил и как нам об этом узнать и что мы будем делать? Это достигается как и всегда с помощью вебхуков. Глобальный бекенд получает запрос со страйпа, обрабатывает его и отправляет запрос на локальный сервер, говоря о том, что оплата была завершена:
```
      ┌───────┐          ┌────────┐                    
      │ Range │          │ Global │                    
      └───┬───┘          └────┬───┘                    
          │                   │payment_intent.succeeded
          │                   │◄──────────             
          │/payment/webhook   │                        
┌─────────┤◄──────────────────┤                        
│         │checkout.session.completed                  
│         │{                  │                        
│         │ session_uid,      │                        
│         │ global_session_uid│                        
│         │}                  │                        
│         │                   │                        
│         │/photo/upload      │                        
│  loading├──────────────────►│                        
│  photos ├──────────────────►│                        
│         ├──────────────────►│                        
│         │/video/upload      │                        
│  loading├──────────────────►│                        
│  videos ├──────────────────►│                        
│         │OK, { success }    │                        
└─────────┼──────────────────►│                        
          │                   │                        
```

 1. Приходит запрос /payment/webhook с type: "checkout.session.completed", что означает, что сессия была оплачена и завершена. В этом запросе хранится session_uid, что является ЛОКАЛЬНЫМ uid сессии.
 2. По session_uid локальный бекенд находит сессию на своей стороне. Именно поэтому и надо было хранить два uid.
 3. Сразу после нахождения сессии, локальный бекенд отправляет ивент payment.checkout_completed, который ловит PaymentSocketGateway и отправляет данные по websocket'ам на фронтенд чтобы отобразить thank you page
 4. Асинхронно локальный бекенд начинает загрузку всех купленных фото и видео с помощью /photo/upload и /video/upload. Пока что глобальный сервер не получает ответа с локального сервера тому изначальному запросу на /payment/webhook.
 5. После того, как всё загружено, локальный сервер формирует ответ и отправляет его. Тут особо никаких данных нет, просто { success: true }.

При этом фото или видео удаляются после загрузке, т.е их невозможно снова купить и освобождается место. 

Таким образом, мы можем создавать сессии, оплачивать дополнительные продукты, но тогда как работает QR код? Т.е вот на тв появляется медиа и qr код и как можно сделать покупку этого одного медиа? Сразу можно сказать: "давайте просто сделаем ссылку по типу `<global_frontend>/range/<range_id>/buy?id=<media_id>`, там будет поле ввода email'а и после ввода будет идти запрос на глобальный сервер, а глобальный сервер создаст сессию и отдаст url", но так сделать нельзя, ведь в таком случае любой человек из дома сможет покупать все медиа со всех range'ей, просто надо будет подбирать id. Поэтому я сделал по другому, вот так:

Локальный сервер должен создать qr код и каким то образом безопасно прокинуть данные на глобальный сервер. Сделано это с помощью подобия jwt. Я изначально хотел использовать jwt, но он не поддерживает ed25519 и мне пришлось реализовывать генерацию токенов с нуля. Так вот: мы генерируем токен, куда записываем id медиа, id range'а и подписываем всё это с помощью сигнатуры, сгенерированной l_skey_signer. Таким образом, глобальный сервер может достать данные, а затем с помощью g_pkey_checker проверить, были ли они действительно сгенерированы локальным сервером или нет. Получится токен в виде:
`{range_id}|{base64url(json)}.{base64url(hash(alg(json)))}`, 

давайте разберём, что будет если кто-то попытается подобрать значения. json - это обычная строка с типом данных:
```
type BuyMediaPayload = 
  | { cid: number, vid: number }
  | { cid: number, p: string }
```
где cid - id клиента, vid - id видео, p - timestamp фотографии полного видео для клиента с id {cid}.

 1. Если кто-то будет менять range_id, но оставлять всё остальное, то глобальный бекенд найдет другой ключ и соответсвенно сигнатура не сойдется
 2. Если кто-то будет менять данные (то есть json), то сигнатура должна тоже будет поменяться и опять же глобальный бекенд не примет такой токен
 3. Ну и если кто-то будет менять сигнатуру, то данные тоже должны будут поменяться, а они не поменяются. При этом правильно сигнатуру подобрать не получится, ведь она генерируется с помощью секретного ключа l_skey_signer.

Выходит, что локальный сервер генерирует абсолютно уникальный и защищённый токен, который уже идёт на глобальный фронтенд (по ссылке в виде `<global_frontend>/bm?t=<token>`), где в поле ввода пользователь должен будет ввести email и затем этот токен с email'ом будет проброшен в /payment/buy_media на глобальном сервере. Глобальный сервер проверит токен, создаст сессию, вернет ссылку на фронтенд и пользователя перекинет на страницу оплаты, а дальше процедура будет идти без изменений.
```
   GET /client/:id/media_token             
  ┌───────┐  │   ┌───────┐      ┌────────┐ 
  │ Kiosk │  │   │ Range │      │ Global │ 
  └───┬───┘  │   └───┬───┘      └────┬───┘ 
      │      ▼       │               │     
      ├─────────────►│               │     
      │  OK, token   │               │     
      │◄─────────────┤               │     
    /payment/buy_media, { token }    │     
──────┼──────────────┼──────────────►├────┐
      │              │ create_session│    │
      │          ┌───┤◄──────────────┤    │
      │          │   │ create_payment│    │
      │          │   ├──────────────►├──┐ │
      │          │   │ OK, { url }   │  │ │

## Global backend

Глобальный бекенд выполняет функции авторизации, аутентификации, обработки платежей, хранения медиа, управления отправкой писем и проксирования запросов на локальный сервер.

### RangeModule

RangeModule выполняет функции взаимодействия с локальными серверами, их создание и удаление. Проксирование запросов мы уже рассмотрели в разделе "rgc", сейчас пройдемся по алгоритмам удаления и создания.

#### Создание range'а

Создание range'а осуществляется глобальным админом по запросу POST /range/admin/create_range. В этом запросе указываются следующие поля (из CreateRangeDto):
```
export class CreateRangeDto {
  ip_address: string;
  name: string;
  owner_user_id: number;
}
```
 1. ip_address - полный url api локального сервера (например http://192.168.1.207:2356/api)
 2. name - название локального сервера для удобства управления
 3. owner_user_id - глобальный админ изначально должен назначить id пользователя, который будет считаться владельцем данного range'а.

Так вот, алгоритм следующий:
 1. Глобальный сервер первым делом должен проверить, вообще доступен ли сервер. Делается это путем отправки запроса GET /ping на локальный сервер. Глобальный сервер ожидает в ответе некоторые данные, по типу версии (version), checker и echo. Тут давать их не буду для безопасности.
 2. Если проверка пройдена, то есть локальный сервер доступен, глобальный сервер создаёт две пары ключей и сохраняет их в базу данных, а запись возвращает (это делает функция RangeService.complexCreateRange)
 3. После этого на локальный сервер отправляется запрос POST /setup/range с ключами, а также с указанием id range'а на глобальном сервере. Это надо, например, для генерации токена оплаты. Т.е чтобы локальный сервер знал свой id на глобальном сервере. Вместе с этим запросом также посылается ключ Initial-Setup, который range проверяет, чтобы убедиться, что именно глобальный сервер делает запрос на setup (ведь ключей там пока ещё нет, нужен некий статичный токен)

При этом надо учесть, что для того, чтобы локальный сервер принял запрос, в .env должно быть прописан ключ Initial-Setup, а также должен быть включен этот режим. Ожидается, что развертывание будет выглядеть так:
 1. Некий человек, который знает как работает система, подключится к пк, который будет выступать в виде локального сервера и развернет проект.
 2. В .env включит Initial-Setup и создаст range как раз вот этим запросом (POST /range/admin/create_range)
 3. После этого локальный сервер перестанет принимать запросы на создание range'a т.к он уже будет создан.
 4. Ну и на всякий случай человек выключит Initial-Setup.

На локальном же сервере по запросу /setup/range:
 1. Проверяется, создан ли уже range
 2. Если нет, то он создаётся
 3. Записывается дефолтный конфиг (SetupService.setupConfig)
 4. Подключается GlobalServerCommunicator (т.е rgc) (GlobalServiceService.createCommunicator)
 5. Создаются все директории (SetupService.createDirectories)
 6. Запускается поиск камер (ProbeService.startDiscovery)

```
     ┌───────┐             ┌────────┐         
     │ Range │             │ Global │         
     └───┬───┘             └───┬────┘         
         │                     │create_range  
         │ GET /ping           │◄──────────   
         │◄────────────────────┤              
         │ OK PingResponse     │              
         ├────────────────────►│

┌─────────────────────┐        │

#### Удаление range'а

Удаление - процесс проще. Осуществляется с помощью эндпоинта DELETE /range/admin/:id на глобальном сервере.

Глобальный сервер сначала удаляет запись range'а (при этом не удаляя медиа, для того чтобы пользователи могли всё равно посмотреть видео или фото), а затем отправляет на range запрос DELETE /range/remove и локальный сервер тоже удаляет свою запись (при этом удаляются ВСЕ данные). Таким образом локальный сервер становится полностью нефункциональным, ведь всё в бекенде крутится вокруг одной записи range (которая была создана в /setup/range). Клиент сам подтвердил такое поведение, что локальный сервер просто перестаёт работать и всё. Я изначально хотел сделать некий флаг, уведомление и удаление через несколько дней. ### PaymentModule

PaymentModule отвечает за оплату. Часть процесса оплаты я уже описал в разделе PaymentModule локального сервера, что дало понимание работы оплаты в целом. В этом разделе же будут описаны детали функционирования PaymentModule на глобальном сервере. 

Во первых, функционал вынесен на глобальный сервер именно тот, который связан со страйпом, для того, чтобы скрыть ключи и абстрагировать локальный сервер от работы со страйпом. Впрочем об этом я писал. Но я не писал о том, как именно глобальный сервер распределяет запросы на страйп.

Начнем с базы данных. Сессии оплаты хранятся в таблице Payment со структурой:
```
{
  id          Int    @id @default(autoincrement())
  checkout_id String @unique

  uid        String  @default(uuid())
  url        String
  invoice_id String
  active     Boolean

  price Int
  email String @default("")

  range_session_uid String
  createdAt         DateTime @default(now())
  updatedAt         DateTime @default(now()) @updatedAt

  range   Range
  Video   Video[]
  Photo   Photo[]
}
```

 1. checkout_id - id intent'а или checkout session'а на stripe
 2. invoice_id - id чека на страйпе
 3. uid, id - уникальный айди
 4. active - завершен или нет
 5. price - общая стоимость оплаты
 6. email - email пользователя, который создал сессию
 7. range_session_uid - uid сессии на локальном сервере
 8. url - ссылка на оплату (если оплата осуществляется по ссылке)

При создании сессии глобальный бекенд получает (как я и писал ранее) CreateCheckoutLinkDto:
```
export class CreateCheckoutLinkDto {
  price: number;
  session_uid: string;
  email: string;
  reader_id?: string;
}
```
 1. price - стоимость в центах
 2. session_uid - uid сессии на локальном бекенде
 3. reader_id - id reader'а на страйпе (reader - это устройства чтения карты, другими словами - терминал).

Стоит заметить, что reader_id опционален, а это значит, что глобальный сервер может работать и без терминала. Это и будет режим работы по qr коду.

Рассмотрим алгоритм создания сессии оплаты.
 1. Проверяется, определён ли reader_id. 
 2. Если определён, то вызывается PaymentService.createTerminalIntent:
  - Осуществляется поиск по базе данных на существование неоплаченной записи с таким же range_session_uid.
  - Если записи нет, то создаётся paymentIntent:
```
intent = await this.stripe.paymentIntents.create({
    currency: 'usd',
    payment_method_types: ['card_present'],
    capture_method: 'automatic',
    amount: payload.price,
});
```
  - Если есть, то берется уже существующий intent. Это надо для того, чтобы не было двойного списания с пользователя в случае двойного запроса (вдруг ошибка какая то)
  - Затем вызывается processPaymentIntent - отправка запроса на высвечивание экрана оплаты на терминале:
```
await this.stripe.terminal.readers.processPaymentIntent(
  payload.reader_id,
  { payment_intent: intent.id },
);
```
  - Создаётся сессия оплаты с `checkout_id: intent.id` и `url: ''` (это важно)
 3. Если reader_id не определён, то вызывается PaymentSession.createCheckoutLink (то есть оплата по ссылке):
  - Создаётся сессия оплаты:
```
await this.stripe.checkout.sessions.create({
  line_items: [
    {
      price_data: {
        currency: 'USD',
        unit_amount: payload.price,
        product_data: {
          name: `Your shooting videos`,
        },
      },
      quantity: 1,
    },
  ],
  customer_email: payload.email,
  mode: 'payment',
  success_url: process.env.PAYMENT_SUCC_URL,
  cancel_url: process.env.PAYMENT_ERR_URL,
});
```
  - В базе данных создаётся запись с `url: session.url` и `checkout_id: session.id`

После этого пользователь оплачивает либо по ссылке, либо через терминал и на глобальный бекенд приходит вебхук payment_intent.succeeded. Этот вебхук обрабатывается функцией PaymentWebhookService.handlePaymentIntentSuccess:
 1. Получается список всех checkout сессий в страйпе по данному intent'у
 2. Если данные найдены, то оплата осуществлялась по qr коду (то есть по ссылке). Это происходит потому, что stripe под капотом у checkout.sessions.create на самом деле создаёт payment intent и затем присваивает его нужной сессии. Дело в том, что происходит это не моментально и нельзя сразу после создания сессии записать id intent'а в базу данных. В этом случае мы можем найти сессию в базе данных по первому результату списка checkout сессий в страйпе (по полю checkout_id) (это потому, что в checkout_id записалась id checkout сессии, а не intent'а)
 3. Если не найдены, значит оплата осуществлялась через терминал, а значит мы можем найти сессию в базе данных по id intent'а из вебхука, ведь в этом случае checkout_id сразу его содержит.
```
const intentSessions = await this.paymentService.stripe.checkout.sessions.list({ payment_intent: intent.id });
const payment = await this.paymentService.findOne({
  checkout_id: intentSessions.data.length > 0 ? intentSessions.data[0].id : intent.id
});
```
 4. По сессии в базе данных мы находим нужный range и посылаем туда checkout.session.completed
 5. После получения ответа (т.е когда все видео и фото были загружены), глобальный сервер отправляет сообщение на почту, указанную в поле email (это происходит с использованием mailgun). HTML для письма генерируется с помощью handlebars в MailingModule. Стоит заметить, что у владельца range есть возможность поменять текст в письме. Поэтому после конца всей процедуры, глобальный сервер делает ещё один запрос на получение конфигурации (а именно значения payment.email.thank_you_text)

### Storing (VideoModule и PhotoModule)

VideoModule и PhotoModule занимаются сохранением медиа. Они используются на этапе upload process в процедуре оплаты.

Они оба создают файл в файловой системе с помощью LocalFileService, но его я описывать не буду. Как нибудь в другой раз. Да и там ничего интересного нет.

Так вот, PhotoModule просто сохраняет картинку как файл, не делая никаких изменений, а VideoModule делает transcoding с помощью ffmpeg. Это и рассмотрим.

Загрузка видео осуществляется с помощью POST /video/upload. В контроллере вызывается функция VideoService.uploadVideo, которая получает путь ко временному файлу, где хранится видео. ffmpeg получает следующие аргументы:
 1. -crf 28 - необходимо для сжатия. Задаёт качество видео кодировщику libx264
 2. -preset veryfast - ускоряет процесс, но увеличивает объем файла.
 3. -c:v libx264 - выбор кодировщика. h264 поддерживается везде, во всех браузерах и на всех устройствах, поэтому он был выбран.
 4. -c:a aac - иногда в safari пропадал звук, поэтому пришлось также делать transcoding аудиодорожки в aac

В итоге мы получаем идеальный mp4 файл с нужной кодировкой, который проигрывается везде и сохраняем его в файловую систему: 
```
const outputFile = await this.fileService.createFile(
  Buffer.alloc(0),
  "mp4"
);
videoTranscoder.save(outputFile.url)
```
(здесь videoTranscoder - это процесс ffmpeg'а).

И да, /photo/upload и /video/upload получают также id сессии оплаты и после создания файла он сразу привязывается к сессии оплаты, так что пользователь может получить нужные медиа.
